# Phase 03 关卡练习：RAG 核心概念

> **关卡目标**：通过 8 个递进式练习，掌握从零构建 RAG 系统、语义分块、向量数据库选型、检索质量评估、API 封装和故障诊断的全链路技能。

## 练习 1：从零构建 Naive RAG

### 目标
不使用 LangChain / LlamaIndex 等高级框架，仅依赖 `sentence-transformers`（嵌入）、`numpy`（相似度）和一个 LLM API（任意），实现一个完整的 `MinimalRAG` 类，包含 `index`、`retrieve`、`generate`、`query` 四个核心方法。

### 要求
- 自备 **5 篇以上中文文档**（每篇 200-800 字，涵盖不同主题），或从维基百科等公开源获取。
- 实现 **固定长度分块**（chunk_size=200 字符，chunk_overlap=50）。
- 使用任一嵌入式模型（建议 `all-MiniLM-L6-v2` 起步）。
- 检索阶段返回 top-k（k=3）最相关块。
- 生成阶段调用 LLM API 将检索块作为上下文生成回答。
- 报告 **前 5 篇文档中 precision@3**（手动标注 5 个查询的正确答案在哪些文档中）。
- 报告生成质量（用另一个 LLM 或人工判断：相关性 1-5，忠实度 1-5）。

### 输入 / 输出规范
| 项目 | 规范 |
|------|------|
| **输入** | 5+ 篇中文文档（.txt 或代码内变量）、5 个中文查询 |
| **输出** | 每个查询的 top-3 检索结果（文档ID + 块文本 + 相似度分数）、生成回答、评估表格 |

### 评分标准（0-5 分）
| 分数 | 标准 |
|------|------|
| 0 | 未提交或无法运行 |
| 1 | 代码有骨架但核心方法为空（`pass`） |
| 2 | 只有 index + retrieve，无 generate |
| 3 | 四个方法均实现但存在明显 bug（如相似度计算错误） |
| 4 | 完整可运行，但缺少评估报告或无中文文档 |
| 5 | 完整可运行，5+ 中文文档，评估表格齐全，代码有类型标注与 docstring |

### 提示
- 嵌入维度可能很高（384 或 768），用 `np.dot` 后记得归一化或改用余弦相似度。
- 生成 prompt 模板建议：`"根据以下参考资料回答问题：\n{context}\n\n问题：{query}\n\n回答："`
- 如果无 LLM API 额度，可临时用 `gpt-3.5-turbo` 或本地 Ollama 模型替代。
- 用 `sklearn.metrics.pairwise.cosine_similarity` 可省去手动实现。

### 预计用时
4-6 小时

## 练习 2：实现语义分块器

### 目标
实现一个 `SemanticChunker` 类，通过计算相邻句子间的嵌入余弦相似度，检测 **相似度骤降点**（dip detection），在这些位置切分文本。将其与固定长度分块器在**同一篇长中文文章**上对比，并可视化两种策略的分界位置。

### 要求
- 输入一篇 **3000+ 字符的中文文章**（可从新闻、论文或政府报告中选取）。
- 实现 `SemanticChunker`：
  - 先用 `re.split(r'(?<=[。！？.!?])')` 进行句子分割。
  - 计算相邻句子间的嵌入余弦相似度。
  - 当相邻句子相似度 **< 0.6** 时，在此处切分（即 chunks 的边界）。
  - 可选：对过短的 chunk（< 100 字符）合并到前一个 chunk。
- 同时用固定长度（chunk_size=500, overlap=50）对同一篇文章分块。
- 对比输出：
  - 两种策略各生成多少个 chunk。
  - 每个 chunk 的长度分布（min, max, mean, std）。
  - **可视化**：在一张图中用不同颜色标注两种策略的分界位置（x 轴 = 字符位置）。

### 输入 / 输出规范
| 项目 | 规范 |
|------|------|
| **输入** | 一篇 3000+ 字符的中文文章（UTF-8 文本） |
| **输出** | 语义分块结果列表、固定长度分块结果列表、统计表格、分界可视化图（PNG 或屏幕输出） |

### 评分标准（0-5 分）
| 分数 | 标准 |
|------|------|
| 0 | 未提交 |
| 1 | 仅实现句子分割，无相似度计算 |
| 2 | 有相似度计算但未实现 dip detection 逻辑 |
| 3 | SemanticChunker 完整但无对比、无可视化 |
| 4 | 有完整对比 + 统计，缺少可视化 |
| 5 | 全部完成：对比表格、可视化、代码可复现 |

### 提示
- `sentence-transformers` 的 `model.encode()` 可一次编码多个句子，传入 list 比逐个调用快很多。
- 可视化建议用 `matplotlib`：x 轴从左到右是字符位置，y 轴用两条水平带，分别标注语义分界和固定长度分界。
- 相似度骤降点可能有连续多个，考虑用合并策略（例如间隔 < 50 字符的边界合并为一个）。

### 预计用时
3-4 小时

## 练习 3：嵌入模型评测

### 目标
在**双语测试集**（10 个查询，涵盖中英文）上评测 **3 种以上嵌入模型**，比较它们的检索精度、推理延迟和成本估算，产出可供选型参考的对比表格。

### 要求
- 准备一个双语测试集：10 个查询（5 中文 + 5 英文），每个查询有 **人工标注的正确答案文档 ID（1-3 个）**。
- 准备一个文档集（至少 20 篇中英文混杂文档）。
- 评测至少 3 种嵌入模型（推荐：`BAAI/bge-small-zh-v1.5`、`moka-ai/m3e-base`、`sentence-transformers/all-MiniLM-L6-v2`）。
- 对每个模型：
  - 将所有文档编码并存入临时向量索引。
  - 对每个查询编码并检索 top-5。
  - 计算 Precision@3 和 Precision@5。
  - 记录单次编码延迟（文档 + 查询）。
- 估算 API 成本（若用本地模型则为 0，但需标注）。
- 输出对比表格：模型名称 | 维度 | Precision@3 | Precision@5 | 平均延迟(ms) | 成本/1000查询。

### 输入 / 输出规范
| 项目 | 规范 |
|------|------|
| **输入** | 20+ 篇双语文档、10 个双语查询 + ground truth |
| **输出** | 对比表格（markdown 格式）、评测脚本、各模型原始结果 |

### 评分标准（0-5 分）
| 分数 | 标准 |
|------|------|
| 0 | 未提交 |
| 1 | 只评测了 1 个模型 |
| 2 | 评测了 2 个模型，缺少中文或英文查询 |
| 3 | 3 个模型，但 ground truth 缺失或对比表格不完整 |
| 4 | 完整评测 + 表格，缺少延迟或成本估算 |
| 5 | 全部完成，表格格式清晰，包含**统计显著性检验**（如 McNemar 检验或 bootstrap） |

### 提示
- 下载模型前确保磁盘空间充足（bge-small 约 100MB，m3e-base 约 400MB）。
- 延迟测试应取多次（>=10 次）的平均值。
- 批量编码文档可大幅降低总延迟——对比单条 vs 批量编码的差异。
- 若网速受限，可先下载 2 个模型完成练习，第 3 个模型的结果标注为"待补测"并说明原因。

### 预计用时
4-5 小时

## 练习 4：向量数据库迁移

### 目标
先将 **1000 条文档**写入 **Chroma**，建立基准查询延迟；然后将全部数据**迁移到 Qdrant**（本地 Docker 或内存模式），验证数据完整性，对比两种数据库的查询延迟。

### 要求
- 生成或收集 1000 条文档（可用 `faker` 生成或从公开数据集截取，每条 50-200 字）。
- 使用同一个嵌入模型（如 `all-MiniLM-L6-v2`）为所有文档生成向量。
- **Phase 1 - Chroma 基准**：
  - 写入 Chroma（PersistentClient 或 ephemeral）。
  - 执行 20 个随机查询，记录每次查询延迟。
  - 输出平均延迟、P50、P95、P99。
- **Phase 2 - 迁移到 Qdrant**：
  - 从 Chroma 读出所有文档及其向量和元数据。
  - 写入 Qdrant（使用 `qdrant-client`，本地内存模式 `:memory:` 或 Docker）。
  - 验证：逐 ID 检查 Qdrant 中是否存在对应文档，向量误差 < 1e-6。
- **Phase 3 - 对比**：
  - 用相同的 20 个查询向量在 Qdrant 上执行检索。
  - 输出 Qdrant 的延迟统计。
  - 并排对比表格。

### 输入 / 输出规范
| 项目 | 规范 |
|------|------|
| **输入** | 1000 条文档 + 20 个查询向量 |
| **输出** | 数据完整性验证报告（通过/失败 + 未通过 ID 列表）、Chroma vs Qdrant 延迟对比表 |

### 评分标准（0-5 分）
| 分数 | 标准 |
|------|------|
| 0 | 未提交 |
| 1 | 仅在 Chroma 上完成，未迁移 |
| 2 | 迁移完成但未做完整性验证 |
| 3 | 完整性验证有但延迟对比缺失或样本量不足 |
| 4 | 全部完成，但延迟统计仅给出均值无分位数 |
| 5 | 全部完成，分位数齐全，验证代码包含向量逐元素误差检查 |

### 提示
- Qdrant 本地内存模式无需 Docker：`QdrantClient(location=":memory:")`。
- Chroma 用 `client.get(include=["embeddings", "metadatas", "documents"])` 获取全部数据。
- 迁移 1000 条 + 384 维向量约几 MB，确认内存充足。
- 延迟测试注意排除首次查询的冷启动开销。

### 预计用时
3-5 小时

## 练习 5：构建 FastAPI RAG 端点

### 目标
实现一个生产就绪的 FastAPI RAG 服务，包含三个端点：`/documents/upload`（上传文档）、`/search`（向量检索）、`/chat/completions`（RAG 对话）。包含错误处理、日志、CORS、OpenAPI 文档。

### 要求
- **POST /documents/upload**：
  - 接收 multipart/form-data，支持单文件或批量上传（.txt, .pdf, .md）。
  - 对 PDF 用 `PyPDF2` 或 `pdfplumber` 提取文本。
  - 自动分块（固定长度，chunk_size=500, overlap=50）。
  - 自动向量化并存入向量库（Chroma 内存模式即可）。
  - 返回 `{"uploaded": N, "chunks_created": M, "document_ids": [...]}`。
- **POST /search**：
  - JSON body: `{"query": "string", "top_k": 5}`。
  - 返回 `{"results": [{"chunk_id": ..., "text": ..., "score": ..., "document_id": ...}]}`。
- **POST /chat/completions**：
  - JSON body: `{"messages": [...], "top_k": 5}`（兼容 OpenAI chat format）。
  - 从最后一条用户消息提取查询，执行检索，将检索结果拼入 system prompt，调用 LLM API 生成回答。
  - 返回 `{"answer": "...", "sources": [...]}`。
- **全局要求**：
  - CORS 允许所有来源（开发模式）。
  - 使用 Python `logging` 模块记录请求与异常。
  - 使用 FastAPI 的 `HTTPException` 做错误处理。
  - Pydantic models 定义请求/响应 schema（OpenAPI 文档自动生成）。

### 输入 / 输出规范
| 项目 | 规范 |
|------|------|
| **输入** | 文档文件（upload）、查询 JSON（search）、对话 JSON（chat） |
| **输出** | JSON 响应，符合上述各端点规范 |

### 评分标准（0-5 分）
| 分数 | 标准 |
|------|------|
| 0 | 未提交 |
| 1 | 仅实现 1 个端点 |
| 2 | 实现 3 个端点但无错误处理/日志 |
| 3 | 3 个端点 + 部分错误处理，缺少 CORS 或 OpenAPI doc |
| 4 | 全部完成，但 PDF 解析或分块缺失 |
| 5 | 全部完成，错误处理覆盖常见场景，日志格式规范，curl 测试通过 |

### 提示
- 用 `python-multipart` 处理文件上传。
- 本地开发可跳过 PDF 解析（仅支持 .txt/.md），但代码中需保留 PDF 解析的异常处理分支。
- 对 LLM API 调用设置超时（`timeout=30`）防止端点挂死。
- 启动命令：`uvicorn app:app --reload --host 0.0.0.0 --port 8000`。
- 访问 `http://localhost:8000/docs` 查看自动生成的 Swagger 文档。

### 预计用时
5-7 小时

## 练习 6：分块策略全面对比

### 目标
在**同一篇长文档**（5000+ 字符）上应用全部 5 种分块策略，对每种策略的分块结果用相同嵌入模型编码，用相同的 5 个测试查询评估检索精度，产出综合对比图表。

### 要求
- 实现或调用以下 5 种分块策略：
  1. **固定长度分块**（Fixed-Length）：chunk_size=500, overlap=50。
  2. **递归字符分块**（Recursive）：用 `["\n\n", "\n", "。", ".", " ", ""]` 作为分隔符优先级递减切分。
  3. **句子分块**（Sentence）：以句号/感叹号/问号为边界，合并至接近 target_size=500。
  4. **语义分块**（Semantic）：复用练习 2 的 SemanticChunker。
  5. **自适应分块**（Adaptive）：优先语义分块，若 chunk > 600 字符则降级用递归分块二次切分。
- 对每种策略，将 chunk 嵌入后建立向量索引。
- 准备 5 个信息检索类测试查询（答案分散在文档不同位置）。
- 对每个查询，用每种策略检索 top-3，记录命中 ground truth 的数量。
- 可视化输出（一张大图包含多个子图）：

  - 子图 2：5 种策略的 chunk 长度分布箱线图。
  - 子图 3：5 种策略 × 5 个查询的检索精度热力图（precision@3）。
  - 子图 4：在文本轴上标注每种策略的分界位置（类似练习 2 的可视化）。

| **输入** | 一篇 5000+ 字符的中文长文、5 个测试查询 + ground truth |
| **输出** | 综合对比大图（PNG，dpi=150）、各策略详细结果表格 |

### 评分标准（0-5 分）
| 分数 | 标准 |

## 练习 7：距离度量实验

### 目标
使用**完全相同的嵌入向量和查询向量**，分别用余弦距离、欧几里得距离、点积、内积四种度量方式计算相似度并排序，比较检索结果的差异，判断哪种度量最优以及差异是否显著。

### 要求
- 准备一个文档集（>= 50 篇文档，分块后 >= 200 个 chunks）。
- 准备 10 个测试查询 + ground truth。
- 所有文档和查询使用同一个嵌入模型编码（如 `all-MiniLM-L6-v2`）。
- 对每种距离度量，计算 top-5 检索结果。
- 对于每个查询，比较 4 种度量的 top-5 结果：
  - 计算 Precision@5。
  - 计算 4 种度量两两之间的 **Jaccard 相似度**（top-5 结果的重叠率）。
  - 计算 4 种度量两两之间的 **Kendall tau 距离**（排名相关性）。
- 统计检验：对精度最高的两种度量做 **配对 t 检验** 或 **Wilcoxon 符号秩检验**，判断差异是否在 p < 0.05 水平显著。
- 可视化：
  - 子图 1：4 种度量的 precision@5 柱状图（带误差棒）。
  - 子图 2：4 种度量两两 Jaccard 相似度热力图。
  - 子图 3：4 种度量两两 Kendall tau 距离热力图。

### 输入 / 输出规范
| 项目 | 规范 |
|------|------|
| **输入** | 50+ 文档（分块后 200+ chunks）、10 个查询 + ground truth |
| **输出** | 统计表格（precision、Jaccard、Kendall tau）、统计检验 p 值、3 个子图 |

### 评分标准（0-5 分）
| 分数 | 标准 |
|------|------|
| 0 | 未提交 |
| 1 | 仅计算了 cosine / euclidean 两种 |
| 2 | 4 种度量均计算但缺少 ground truth 评估 |
| 3 | 有评估但缺少统计检验 |
| 4 | 统计检验有但可视化不完整 |
| 5 | 全部完成，统计检验方法选择合理，结论清晰 |

### 提示
- 注意：**余弦距离 = 1 - 余弦相似度**；余弦相似度和点积在向量已归一化时等价；欧几里得距离与余弦距离在向量已归一化时单调相关。
- 使用 `scipy.stats` 中的 `wilcoxon` 或 `ttest_rel` 做配对检验。
- 用 `scipy.stats.kendalltau` 计算排名相关性。
- 如果两种度量等价（如归一化后的 cosine 和 dot），Jaccard 应接近 1.0。

### 预计用时
3-5 小时

## 练习 8：诊断 Naive RAG 幻觉根因

### 目标
给定一个会产生幻觉的 Naive RAG 系统，系统地诊断根因（检索质量差、上下文截断、prompt 设计不当、生成模型温度过高、知识冲突等），提出并实现修复方案，展示修复前后的生成质量对比。

### 要求
- 构造或获取一个 **会触发幻觉的 Naive RAG 场景**。设计场景使系统至少暴露出 2 种问题（例如：检索到不相关文档 + prompt 未约束"不知道就说不知道"）。
- 诊断步骤（输出诊断报告）：
  1. **检索诊断**：检查 top-k 检索结果是否真正与查询相关。计算 precision@k 和 recall@k。
  2. **上下文诊断**：检查拼接后的 context 是否超过 LLM 的上下文窗口或是否包含矛盾信息。
  3. **Prompt 诊断**：检查 prompt 是否指示模型在无相关信息时拒绝回答。
  4. **生成诊断**：检查生成参数（temperature, max_tokens）是否合理。
  5. **知识诊断**：检查生成内容中哪些信息不在 context 中（幻觉片段标注）。
- 实施修复（至少修复 2 个问题）：
  - 例如：引入**重排序（reranker）**提升检索精度。
  - 例如：优化 prompt 模板，加入"仅根据提供的参考资料回答，若无相关信息请明确说明"。
  - 例如：降低 temperature 或加入 self-consistency check。
- 对比修复前后：
  - 同一组 5 个查询的生成结果。
  - 用幻觉检测指标（如：生成内容中不在 context 中的实体比例）。
  - 用另一个 LLM 对回答的忠实度评分（1-5）。

### 输入 / 输出规范
| 项目 | 规范 |
|------|------|
| **输入** | 一个存在幻觉问题的 Naive RAG 系统代码、5 个测试查询 |
| **输出** | 诊断报告（markdown）、修复后代码、修复前后对比表 |

### 评分标准（0-5 分）
| 分数 | 标准 |
|------|------|
| 0 | 未提交 |
| 1 | 仅在口头上描述了问题，无系统诊断 |
| 2 | 做了诊断但只识别了 1 个根因 |
| 3 | 识别 2+ 根因但修复仅解决 1 个 |
| 4 | 修复 2+ 问题，有前后对比但缺少量化指标 |
| 5 | 全部完成：诊断报告、修复代码、量化对比、忠实度评分 |

### 提示
- 构造幻觉场景的常见手段：故意使用过短的 chunk、移除 reranker、使用高 temperature、prompt 中不限制信息来源。
- 幻觉检测可以用简单方法：提取生成文本中的命名实体，检查是否出现在 context 中。
- 忠实度评分可调用另一个 LLM 做 judge："以下回答是否完全基于给定的参考资料？请给出 1-5 分并说明理由。"
- 重排序可用 `cross-encoder/ms-marco-MiniLM-L-6-v2`（HuggingFace）。
