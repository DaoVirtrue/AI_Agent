# D1-02：自建 vs 平台 vs SaaS —— 3D 决策矩阵

> **核心问题**：我有 AI 需求，应该自己建、用开源平台部署、还是买 SaaS？
> **前提**：你已了解 RAG 技术栈（Track A-C），现在做商业决策。

---

## 一、三种模式的本质区别

| 维度 | 自建 (DIY) | 平台 (Platform) | SaaS |
|------|-----------|----------------|------|
| **定义** | 基于开源框架从零搭建 | 部署开源/商业平台到自有环境 | 购买云服务 API |
| **控制权** | 100% | 80% | 20% |
| **定制能力** | 无限 | 有限（平台约束内） | 极少（配置项） |
| **初始投入** | 6-12 人月 | 1-3 人月 | 1 天-1 周 |
| **持续投入** | 1-2 人持续维护 | 0.5 人运维 | 0 人 |
| **上线速度** | 3-6 个月 | 2-4 周 | 1-3 天 |
| **数据主权** | 完全自有 | 完全自有 | 数据在第三方 |
| **技术门槛** | 高（需 AI 团队） | 中（需运维团队） | 低（任何人） |
| **长期 TCO** | 最低（2年+） | 中等 | 最高 |
| **代表方案** | LangChain+LlamaIndex | RAGFlow/Dify 私有化 | OpenAI/Cohere API |

---

## 二、3D 决策矩阵

### 维度 1：团队能力 (Team Capability)

```
你的团队有什么能力？

  无 AI 研发能力 ──→ SaaS（门槛最低）
  │
  有运维但无 AI 研发 ──→ 平台（RAGFlow/Dify 私有化部署）
  │
  有 AI 研发能力 ──→ 评估另外两个维度
```

### 维度 2：定制化需求 (Customization)

```
你需要多深的定制？

  标准 RAG（知识库+问答）──→ SaaS 或 平台
  │
  需要自定义检索/存储/模型链 ──→ 平台
  │
  需要完全自定义的全链路 ──→ 自建
  │
  需要嵌入到自己产品中 ──→ 自建（或平台 API 模式）
```

### 维度 3：时间线 (Timeline)

```
多长时间内必须上线？

  < 1 周 ──→ SaaS（唯一可行选项）
  │
  1-4 周 ──→ 平台（RAGFlow/Dify）
  │
  1-3 个月 ──→ 平台先行，后续自建替换
  │
  > 3 个月 ──→ 自建
```

## 三、四大场景深度分析

### 场景 1：创业公司，3 人，2 周上线 MVP

```
团队：1 后端 + 1 前端 + 1 产品
预算：5 万/月
需求：智能客服 MVP

决策路径：
  时间线 < 2周 → 排除自建
  团队无 AI → 排除自建
  → 二选一：SaaS 或平台

  SaaS 路线：
    用 OpenAI API + Pinecone SaaS
    成本：~$2000/月（5000 次查询）
    优点：零运维，上线最快
    缺点：数据在外，定制受限

  平台路线：
    Dify 私有化部署（1台云服务器）
    成本：~$500/月（服务器）+ $1500/月（LLM API）
    优点：数据自己掌控，后续可升级
    缺点：需要 1-2 天部署

  推荐：平台路线（Dify + 1台服务器）
  理由：数据在自己手里，后续可以做私有化交付给客户。
```

### 场景 2：中型企业，10 人团队，3 个月内部平台

```
团队：3 算法 + 5 后端 + 2 前端
预算：200 万/年
需求：企业级 AI 中台（服务多个业务线）

决策路径：
  团队有 AI 研发 → 自建可行
  定制需求高（多业务线、复杂权限）→ 倾向自建
  时间线 3 个月 → 自建可行

  推荐：自建（LlamaIndex + LangGraph + 自研业务层）

  分阶段实施：
  第1月：基于 LlamaIndex 搭建核心 RAG 管道
  第2月：用 LangGraph 构建 Agent 工作流 + 权限系统
  第3月：多业务线接入 + 管理后台 + 压测上线
```

### 场景 3：传统企业，无 AI 团队，安全要求高

```
团队：IT 运维 3 人，无研发
需求：内部知识库问答，数据不能出内网
预算：30 万/年

决策路径：
  数据不能出内网 → 排除 SaaS
  无 AI 研发 → 排除自建
  → 唯一选项：平台（私有化部署）

  推荐：RAGFlow 或 Dify 企业版（私有化部署）

  实施路径：
  1. 由供应商或咨询团队完成初次部署和配置（2周）
  2. IT 部门负责文档导入和日常运维
  3. 业务部门通过 Web UI 使用
  4. 持续导入新文档，维护知识库质量
```

### 场景 4：SaaS 产品，已有研发，需嵌入 AI 功能

```
团队：20+ 研发，已有成熟 SaaS 产品
需求：在产品中增加 AI 问答功能，多租户
预算：充足（核心战略）

决策路径：
  需嵌入到自有产品 → 平台 API 或自建
  多租户数据隔离要求 → 平台受限
  已有研发团队 → 自建可行

  推荐：自建（核心能力）+ 策略性使用 SaaS（非核心）

  架构：
  检索层：LlamaIndex（多租户向量索引隔离）
  编排层：LangGraph（Agent 工作流）
  LLM：自建路由（GPT-4o 主 + DeepSeek 降级）
  存储：Milvus（向量）+ PostgreSQL（元数据）
```

## 五、混合策略：最佳实践

### 策略 1：SaaS 起步 → 平台过渡 → 自建收尾

```
阶段1 (0-3月): SaaS
  → 验证市场需求，收集用户反馈
  → 成本低、速度快，试错代价小

阶段2 (3-6月): 平台
  → 数据量增长，SaaS 成本上升
  → 迁移到 Dify/RAGFlow 私有化
  → 开始定制功能

阶段3 (6-12月): 自建
  → 平台限制成为瓶颈
  → 用 LlamaIndex/LangChain 重构建
  → 完全掌控技术栈
```

### 策略 2：核心自建 + 非核心 SaaS

```
核心功能（自建）：
  - RAG 检索管道（核心竞争力）
  - 多租户权限系统
  - 业务编排逻辑

非核心功能（SaaS）：
  - LLM API（按需切换多个供应商）
  - 代码生成辅助（GitHub Copilot）
  - 监控和日志（Datadog/Grafana Cloud）
```

### 策略 3：平台为壳 + 自建为核

```
Dify/RAGFlow 提供：
  - 知识库管理 UI
  - 文档导入和解析
  - 基础的检索和问答

自建增强：
  - 自定义检索算法（替换默认检索器）
  - 自定义 Agent 工作流（LangGraph 集成）
  - 自定义权限和审计
```

## 六、决策检查清单

- [ ] 团队有 AI 研发能力吗？
- [ ] 数据可以出内网吗？
- [ ] 需要多租户数据隔离吗？
- [ ] 需要完全白标（去品牌化）吗？
- [ ] 上线时间紧迫程度？(< 2周, 2-4周, > 1月)
- [ ] 预期使用量（日均查询次数）？
- [ ] 长期（3年+）还是短期项目？
- [ ] 需要嵌入到现有产品中吗？
- [ ] 预算约束是什么？
- [ ] 未来可能需要切换方案吗？（考虑可移植性）

**快速判断**：
- 如果"无 AI 研发" + "数据可出内网" → SaaS
- 如果"无 AI 研发" + "数据不可出内网" → 平台
- 如果"有 AI 研发" + "需要深度定制" → 自建
- 如果"有 AI 研发" + "时间紧迫" → 平台先行，后续自建
