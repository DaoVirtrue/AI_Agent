# S3-05：客服 Agent 案例 —— 多租户 SaaS 智能客服

---

## 一、业务背景

某智能客服 SaaS 公司服务 300+ 企业客户，覆盖电商、金融、教育、医疗等行业。
每个客户有独立的知识库、对话策略、品牌形象。日均总对话量 200 万次。

**核心需求**：
- 多租户 SaaS 架构（每个客户数据完全隔离）
- 智能意图识别与自动路由（产品咨询 → 知识库 / 投诉 → 升级人工 / 订单 → API 查询）
- 知识库持续更新（客户新增 FAQ → 自动生效，无需重新部署）
- 满意度指标闭环（用户反馈 → 自动分析 → 改进策略）
- 支持 1000+ 并发会话

## 三、关键决策

### 决策 1：共享基础设施 vs 独立实例

**选择**：共享基础设施（多租户逻辑隔离 + 关键数据物理隔离）

**实现**：
- 向量库：每个租户独立的 Qdrant Collection（物理隔离）
- LLM 调用：共享 API 池，但会话级隔离
- 数据库：共享 PostgreSQL 但租户级行级安全（RLS）
- 大客户（Top 20）：独立部署实例（可选升级）

### 决策 2：意图识别层次

**选择**：粗分类（LLM）+ 细分类（关键词）两级意图识别

**实现**：
- 第一级（LLM）：将用户问题分为 8 大类
  - 产品咨询 / 订单查询 / 投诉建议 / 技术问题 /
    退款售后 / 账户问题 / 闲聊 / 其他
- 第二级（关键词 + 规则）：
  - "退款"类 → 退款原因细分（质量/物流/不想要/其他）
  - 不同细分走不同的对话流程

### 决策 3：知识库更新的实时性

**选择**：区分"热更新"和"冷更新"

**实现**：
- 热更新（FAQ 增删改）：实时生效（更新缓存 + 即时索引）
- 冷更新（文档上传）：异步处理（上传 → 排队 → 解析 → 索引 → 通知完成）
- 效果：FAQ 修改后 30 秒内生效，大文档上传后 5-10 分钟生效

## 四、数据管道设计

```
客服知识管理管道：

1. 客户自助上传
   → Web 界面上传 FAQ（表格/CSV）
   → 自动校验（问题-答案成对、无空行、无重复）
   → 即时索引（FAQ 专用快速通道）
   → 测试面板（客户可即时测试新 FAQ 的效果）

2. 文档知识沉淀
   → 上传产品手册/使用指南 PDF
   → 异步解析队列
   → DeepDoc 深度解析（表格/图片/章节结构）
   → 语义分块 → 嵌入 → 索引
   → 通知客户"文档已就绪"

3. 对话知识挖掘
   → 每日分析"转人工"的对话
   → 聚类：哪些问题 AI 解决不了
   → 生成知识库补充建议
   → 推送客户："检测到以下问题暂无覆盖，建议添加"
   → 客户一键采纳 → 自动入库

4. 满意度闭环
   → 每次对话后收集用户反馈（👍/👎）
   → 点踩的回答 → 自动分析原因（知识库缺失/回答不准/格式问题）
   → 推送到运营后台
   → 运营人员修复 → 重新上线 → 监控效果
```

## 五、准确率优化

```
客户满意度从 72% → 91%：

优化1：租户级定制 Prompt (72% → 78%)
  问题：通用 Prompt 无法体现客户品牌调性
  方案：每个租户可自定义系统 Prompt
        （"你是XX品牌的客服"vs"你是专业的售后顾问"）
  效果：品牌一致性提升满意度

优化2：意图识别准确率 (78% → 83%)
  问题：用户说"买了3天能退吗"被识别为"产品咨询"而非"退款售后"
  方案：增加退款/售后类关键词权重，LLM 做二次确认
  效果：路由准确率从 82% 提升到 94%

优化3：知识覆盖度 (83% → 87%)
  问题：客户的知识库覆盖不全，很多问题无答案
  方案：自动分析未覆盖问题 → 推送补充建议
  效果：知识覆盖率从 65% 提升到 85%

优化4：多轮对话 (87% → 89%)
  问题：用户需要追问才能得到满意回答
  方案：增加主动澄清（"您是问退款政策还是退款进度？"）
  效果：首轮解决率从 68% 提升到 76%

优化5：人工协同 (89% → 91%)
  问题：AI 不会的问题直接转人工，用户体验断层
  方案：AI 先整理好问题上下文 → 转人工时展示给客服
  → 客服快速了解情况，减少重复问询
  效果：转人工后的满意度也从 70% 提升到 85%
```

## 七、踩坑记录

### 坑1：多租户的 Prompt 互相"污染"

```
问题：某些 LLM 提供商在共享计算资源时，不同租户的请求
      可能在后端被缓存混淆。
      租户A的品牌名出现在租户B的回答中。
教训：为每个租户使用不同的 API Key（即使是同一供应商）。
      在应用层做租户标识注入，确保不会串号。
      LLM 调用日志中记录租户 ID → 可追溯。
```

### 坑2：客户的"差"FAQ 污染知识库

```
问题：客户自主上传的 FAQ 质量参差不齐。
      有的 FAQ 写得太简略（"退款：联系客服"），
      有的直接错误。
影响：错误 FAQ 导致 AI 给用户错误答案。
解决：增加 FAQ 质量检测：
      - 答案长度检测（< 10 字拒绝）
      - 矛盾检测（同一问题不能有两个不同答案）
      - 客户上传后需通过"测试面板"验证才生效
```

### 坑3：满意度调查的幸存者偏差

```
问题：只有"特别满意"和"特别不满意"的用户会填写反馈。
      导致满意度数据严重偏态。
教训：不要只看满意度百分比。
      监控"未评价率"——如果超过 80%，说明数据不可靠。
      增加隐性指标：用户是否追问、用户是否转人工、
      用户是否在对话中表达了情绪。
```

## 八、经验教训

1. **多租户 SaaS 的知识库隔离是最大技术挑战**。不是简单的"加个 tenant_id 过滤"。
2. **客户的 FAQ 质量决定了 AI 客服的质量**。垃圾进垃圾出，必须做好上传前的质量把关。
3. **满意度指标需要多维验证**。单一 NPS 分数不可信，要结合隐性行为指标。
4. **知识库的"自我进化"能力是关键差异化**。自动发现空白 + 推送补充建议 = 持续变好。
5. **人工协同不是失败，是设计的一部分**。AI 不能解决所有问题，但可以让转人工的体验更好。
6. **每个租户应有独立的效能仪表盘**。客户需要看到 AI 为他们带来的价值（解决了多少问题、节省了多少人力）。
