# S3-04：金融 RAG 案例 —— 合规文档检索与研报分析

---

## 一、业务背景

某头部券商（管理资产规模 2 万亿+）需要提升合规审查和研报分析的效率。
合规部门每天需要审查数百份文件是否违反监管规定；
研究部门需要快速消化海量研报、公告、新闻，支持投资决策。

**核心需求**：
- 自动化金融合规检查（文档是否违反证监会/交易所规定）
- 研报智能摘要与分析（多份研报的交叉验证）
- 监管规则实时更新（新规发布后 24 小时内生效）
- 完整审计追踪（每一份被审查的文档的完整记录）
- 严格的数据隔离（不同业务部门之间数据不能互通）

## 三、关键决策

### 决策 1：租户级向量隔离

**选择**：每个业务部门独立的向量集合（Qdrant Collection）

**原因**：
- 金融监管要求投行和研究部门之间有严格的"信息隔离墙"（Chinese Wall）
- 同一向量库中即使加 metadata 过滤，仍有跨部门泄露风险
- 物理隔离 > 逻辑隔离
- 代价：存储成本增加 3-5 倍，但合规部门认为"必要且合理"

### 决策 2：监管规则的知识表示

**选择**：规则向量化 + 规则决策树双引擎

**实现**：
- 每条监管规则提取为"IF (条件) THEN (禁止/要求/限制)"的结构
- 向量引擎：找到"相关的"监管规则
- 规则引擎：对找到的规则做精确匹配判断
- 例如："上市公司董事在定期报告发布前 30 日内不得买卖本公司股票"
  - 向量找到这条规则
  - 规则引擎判断：当前日期 vs 报告发布日期 → 是否在窗口期内

### 决策 3：审计日志的不可篡改性

**选择**：WORM（Write Once Read Many）存储 + 区块链哈希锚定

**实现**：
- 所有查询日志写入 WORM 存储（如 AWS S3 Object Lock）
- 每小时将日志哈希写入区块链（防内部篡改）
- 监管检查时可以验证日志自生成后从未被修改

## 四、数据管道设计

```
金融数据管道：

1. 监管规则同步（T+1，紧急情况实时）
   → 爬取证监会/交易所/央行官网
   → PDF/HTML → 结构化提取（规则号/标题/正文/生效日期/处罚条款）
   → 规则提取：LLM 将规则文本转为 IF-THEN 结构化表示
   → 写入监管规则知识库
   → 新旧规则对比 → 标记变更/废止

2. 研报数据同步（每日）
   → 对接 Bloomberg/Wind/东方财富 API
   → 研报 PDF → 结构化解析
   → 提取：行业/公司/评级/目标价/核心观点/风险提示
   → 嵌入 + 索引

3. 公告数据同步（准实时）
   → 沪深交易所公告 API（延迟 < 5 分钟）
   → 分类：定期报告/临时公告/重组公告/停复牌
   → 紧急公告（如"重大资产重组"）优先级最高
   → 实时索引

4. 合规文档审查管道
   → 业务部门提交待审查文档
   → 自动匹配相关监管规则
   → 逐条比对：文档内容 vs 规则 IF 条件
   → 生成合规审查报告（通过/风险/违规）
   → 人工合规官复核
```

## 五、准确率优化

```
合规审查准确率从 85% → 96%：

优化1：规则结构化 (85% → 90%)
  问题：监管规则的向量检索不够精确
  方案：将每条规则 LLM 提取为 IF-THEN 结构化规则
  效果：精确匹配率大幅提升

优化2：多源规则交叉验证 (90% → 93%)
  问题：单一来源的规则可能不完整
  方案：同时检索证监会官网 + 法律数据库 + 内部解读
        三者交叉验证，取最严格的解释
  效果：减少了漏报

优化3：时间敏感过滤 (93% → 95%)
  问题：文档日期在规则生效前 → 不应适用该规则
  方案：加入时间维度（文档日期 vs 规则生效日期 vs 废止日期）
  效果：消除了时间不匹配的误报

优化4：行业个性化规则库 (95% → 96%)
  问题：通用规则审查忽略了行业特殊规定
  方案：为每个行业维护专属规则增量库
```

## 七、踩坑记录

### 坑1：规则冲突时的优先级

```
问题：证监会规定 A 和交易所规定 B 对同一问题有不同要求。
      系统应该以哪个为准？
教训：建立了规则优先级体系：
      L1: 全国人大法律
      L2: 国务院行政法规
      L3: 证监会部门规章
      L4: 交易所自律规则
      L5: 行业协会指引
      冲突时取更严格者，并同时标注两个规则的差异。
```

### 坑2：信息隔离墙的"漏洞"

```
问题：技术上隔离了不同部门的向量库，但 LLM 可能"记住"了跨部门信息。
      例如研究部的研报内容被 LLM 在回答投行部问题时"无意"泄露。
教训：每部门的 LLM 会话必须独立。禁止跨部门的 conversation history 共享。
      对 LLM 输出增加"信息泄露检测"——检测是否包含其他部门的专有信息。
```

### 坑3：紧急规则的延迟

```
问题：周五下午 5 点发布紧急监管新规，周一上午 9 点生效。
      周五下班 → 周末无人处理 → 周一来不及更新。
教训：建立 7×24 紧急规则响应机制。
      规则变更检测（自动化）→ 紧急程度判定（自动化）
      → 高紧急 → 自动更新索引 + 通知全员
      → 中紧急 → 放入队列等待人工确认
```

## 八、经验教训

1. **金融合规不是"检索"，而是"规则匹配"**。需要规则引擎 + RAG 双引擎协作。
2. **数据隔离是金融系统的第一优先级**。不是技术问题，是监管要求。
3. **审计日志不只是"日志"**。必须是不可篡改的、可独立验证的。
4. **规则优先级冲突是常态**。系统必须有明确的优先级逻辑。
5. **"信息隔离墙"的维护不只是技术问题**。需要流程、制度、培训的共同保障。
