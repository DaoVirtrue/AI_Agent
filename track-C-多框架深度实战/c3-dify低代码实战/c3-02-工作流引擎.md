# C3-02：Dify 工作流引擎详解

> **核心能力**：通过可视化拖拽的方式构建复杂的 AI 工作流，支持条件分支、循环、代码执行、插件扩展。
> **对比**：类似 LangGraph 的可视化版本，但学习成本降低 90%。

---

## 二、节点类型全览

### 2.1 节点分类

| 类别 | 节点 | 功能 |
|------|------|------|
| **开始/结束** | 开始 | 定义输入变量，工作流入口 |
| | 结束 | 定义输出变量，工作流出口 |
| **LLM** | LLM | 调用大语言模型生成文本 |
| | 知识检索 | 从知识库检索相关内容 |
| | 问题分类 | LLM 将问题分到预设类别 |
| **逻辑** | 条件分支 (IF/ELSE) | 根据条件选择执行路径 |
| | 迭代 (Iterator) | 遍历数组，逐项处理 |
| | 变量聚合 (Variable Aggregator) | 将多个分支结果合并 |
| **工具** | 代码节点 | 执行 Python/JS 代码 |
| | HTTP 请求 | 调用外部 API |
| | 工具调用 | 调用配置的插件工具 |
| **数据处理** | 模板转换 | Jinja2 模板渲染文本 |
| | 变量赋值 | 设置/修改变量值 |
| | 参数提取 | 从文本中结构化提取参数 |

### 2.2 节点详解

#### LLM 节点

```yaml
配置项:
  模型: "GPT-4o / Claude Sonnet 4 / Qwen-Max / DeepSeek-V3"
  上下文: "引用上游节点输出（如知识检索结果）"
  提示词: |
    你是一个专业的技术支持助手。
    请基于以下知识库内容回答用户问题。

    知识库内容：
    {{#context#}}

    用户问题：
    {{#query#}}

    要求：
    1. 如果知识库没有相关信息，明确说明
    2. 引用来源时标注文档名称
    3. 回答简洁清晰，不超过 300 字
  记忆: "开启/关闭（多轮对话上下文）"
  输出变量: "text (生成的回答)"
```

#### 知识检索节点

```yaml
配置项:
  知识库: "选择已创建的知识库（可多选）"
  检索模式: "混合检索"
  查询内容: "{{#query#}} 或自定义表达式"
  Top K: 3
  分数阈值: 0.5
  重排序: "开启 (BGE-Reranker)"
  输出变量: "result (检索到的文档列表)"
```

#### 条件分支节点

```yaml
配置方法:
  - 条件表达式: 基于变量值判断
  - LLM 判断: 让 LLM 根据语义判断走哪个分支
  
示例：
  IF {{#intent}} == "产品咨询":
    → 走产品知识库检索
  ELIF {{#intent}} == "技术支持":
    → 走技术文档检索
  ELSE:
    → 转人工客服
```

#### 代码节点

```python
# 在 Dify 工作流中执行的 Python 代码（沙箱环境）

def main(context: dict) -> dict:
    """
    输入：上游节点的输出变量，通过 context 字典传入
    输出：返回字典，会成为下游节点的输入变量
    """
    # 获取上游数据
    user_query = context.get("query", "")
    retrieved_docs = context.get("knowledge_result", [])

    # 自定义处理逻辑
    # 例如：对检索结果进行后处理
    filtered_docs = []
    for doc in retrieved_docs:
        # 过滤掉相关度太低的结果
        if doc.get("score", 0) > 0.6:
            filtered_docs.append({
                "content": doc["content"][:1000],  # 截断过长内容
                "source": doc.get("document_name", "unknown"),
                "score": doc["score"],
            })

    # 重新组织上下文
    formatted_context = "\n\n---\n\n".join(
        f"[来源: {d['source']}] (相关度: {d['score']:.2f})\n{d['content']}"
        for d in filtered_docs[:5]
    )

    return {
        "filtered_context": formatted_context,
        "doc_count": len(filtered_docs),
        "avg_score": sum(d["score"] for d in filtered_docs) / len(filtered_docs)
        if filtered_docs else 0,
    }
```

#### HTTP 请求节点


## 三、变量系统

### 3.1 变量类型

| 变量类型 | 作用域 | 示例 |
|----------|--------|------|
| 输入变量 | 工作流入口 | `query`, `user_id`, `language` |
| 节点输出变量 | 单个节点 | `llm.text`, `knowledge.result` |
| 环境变量 | 工作流全局 | `api_key`, `base_url`, `model_name` |
| 会话变量 | 整个会话（多轮） | `conversation_history`, `user_context` |

### 3.2 变量引用语法

```jinja2
{# 引用输入变量 #}
{{#query#}}

{# 引用节点输出 #}
{{#llm_node.text#}}

{# 在提示词中遍历数组 #}
{% for doc in knowledge_result %}
来源: {{doc.document_name}}
内容: {{doc.content}}
{% endfor %}

{# 条件表达式（在条件分支中使用）#}
{{#intent}} == "产品咨询"

{# 数学运算 #}
{{#price}} * {{#quantity}}
```

## 四、高级工作流模式

### 4.1 意图识别 + 路由

```
[开始] → [问题分类(LLM)] → [条件分支]
                               ├── "产品咨询" → [产品知识库检索] → [LLM回答]
                               ├── "技术支持" → [技术文档检索] → [LLM回答]
                               ├── "投诉"     → [情感分析] → [升级处理]
                               └── "其他"     → [通用LLM回答]
                              ↓
                         [变量聚合] → [结束]
```

### 4.2 多轮对话增强

```
[开始]
  ├── 读取 {{#conversation_history}}
  ├── 提取对话中的关键实体
  └── [知识库检索] ← 用实体+问题联合查询
       ↓
     [LLM 节点]
       ├── 系统提示词引用对话历史
       ├── 上下文引用检索结果
       └── 输出: 回答 + 更新的对话状态
       ↓
     [结束]
       └── 返回 {{#answer}}
```

### 4.3 自我反思循环

```
[开始] → [LLM生成初版回答]
           ↓
         [质量检查(LLM)]
           ├── 通过 → [结束]
           └── 不通过 → [优化提示词]
                          ↓
                        [重新生成] → 回到质量检查
                        (最多循环3次)
```

### 4.4 并行检索 + 融合

```
                [开始]
                   ↓
         ┌─────────┼─────────┐
         ↓         ↓         ↓
    [知识库A检索] [知识库B检索] [外部API]
         ↓         ↓         ↓
         └─────────┼─────────┘
                   ↓
            [结果合并(代码节点)]
                   ↓
         [去重 + 按相关度排序]
                   ↓
              [LLM综合回答]
                   ↓
                [结束]
```

## 六、Dify 工作流 vs LangGraph

| 维度 | Dify 工作流 | LangGraph |
|------|------------|-----------|
| 操作方式 | 可视化拖拽 | Python 代码 |
| 学习成本 | 低（1天上手） | 高（需理解图/状态/边） |
| 调试体验 | 可视化单步调试 | 日志+LangSmith |
| 复杂度上限 | 中等（画布限制） | 极高（任意代码） |
| 人机协同 (HITL) | 支持（通过工具调用） | 原生支持 (interrupt) |
| 版本管理 | 内置 | Git |
| 部署 | 一键发布 API | 需自建部署 |
| 适用团队 | 全角色（含非技术人员） | 开发团队 |

**结论**：简单到中等复杂度的工作流用 Dify，高度复杂的自定义编排用 LangGraph。
