# C2-04：RAGFlow vs DIY RAG —— 何时用平台，何时自建

> **核心问题**：我有开发能力，应该用 RAGFlow 还是自己搭建 RAG 系统？
> **前置阅读**：Track A（RAG 理论）+ C2-01（无切片范式）

## 一、决策框架总览

```
                          你是否需要 RAGFlow？

         ┌─────────────────────────────────────────────┐
         │  你的团队情况是什么？                        │
         │                                               │
         │  A: 3人以下 + 1周上线        → RAGFlow         │
         │  B: 5人以上 + 持续迭代       → DIY RAG         │

         └─────────────────────────────────────────────┘
```

## 二、功能维度逐项对比

### 2.1 文档解析能力

| 能力 | RAGFlow | DIY（LangChain+LlamaIndex） |
|------|---------|----------------------------|
| PDF 解析 | DeepDoc 深度解析（表格/图片/公式） | PyPDF/pdfplumber（基础） |
| 表格识别 | 内置，自动提取为结构化数据 | 需自建（Unstructured/Table Transformer） |
| OCR | 内置（支持扫描件） | 需集成 Tesseract/PaddleOCR |
| 文档结构保留 | 自动识别章节/标题层次 | 手动实现层级结构 |
| 多语言混合文档 | 原生支持 | 需额外处理 |
| 扫描件处理 | 内置 OCR + 布局分析 | 需集成多个库 |

**结论：文档解析是 RAGFlow 最明显的优势。如果文档格式复杂（扫描件、表格、多语言），选 RAGFlow。**

### 2.2 分块策略

| 策略 | RAGFlow | DIY |
|------|---------|-----|
| 固定大小分块 | ✅ | ✅ |
| 语义分块 | ✅ | ✅ |
| 按文档类型分块 | ✅ 原生支持 10+ 种 | ❌ 需手动实现 |
| 表格保留分块 | ✅ 自动提取 | ❌ 需手动处理 |
| Q&A 分块 | ✅ | ❌ |
| 法律条款分块 | ✅ | ❌ |
| 知识图谱分块 | ✅ | ❌ |

### 2.3 检索能力

| 能力 | RAGFlow | DIY |
|------|---------|-----|
| 向量检索 | ✅ | ✅ |
| 全文检索（BM25） | ✅ 内置 ES | 需集成 ES/BM25 |
| 混合检索 | ✅ 内置融合 | 需手动实现 RRF |
| 知识图谱检索 | ✅ 内置 GraphRAG | 需自建 |
| 多模态检索 | ✅ | 需大幅自建 |
| 重排序 | ✅ | 需集成 Reranker |

### 2.4 管理与运营

| 能力 | RAGFlow | DIY |
|------|---------|-----|
| Web UI 管理界面 | ✅ 开箱即用 | ❌ 需自建 |
| 文档生命周期管理 | ✅ | ❌ |
| 用户/角色权限 | ✅ | ❌ |
| 审计日志 | ✅ 部分 | 需自建 |
| 多租户 | ✅ | 需自建 |
| 数据统计看板 | ✅ | 需自建 |

## 三、四场景深度分析

### 场景 A：创业团队，3 人，2 周内需要上线智能客服

**背景**：
- 团队 3 人（1 后端 + 1 前端 + 1 产品）
- 需要快速上线 MVP
- 文档量 500-1000 篇，含 PDF 扫描件和表格
- 预算有限

**分析**：
- DIY 路线：至少需要 2 个月（文档解析 2 周 + 检索 2 周 + UI 2 周 + 测试 2 周）
- RAGFlow 路线：部署 1 天 + 文档导入 2 天 + API 集成 2 天 + 前端 5 天 = 约 2 周

**推荐：RAGFlow**
- 文档解析零成本（DeepDoc 处理扫描件和表格）
- Web UI 直接可用，前端只需调用 API
- 后续若需要深度定制，再渐进式替换组件

**风险**：
- RAGFlow 社区版的并发和稳定性需验证
- 深度定制能力有限

---

### 场景 B：中大型企业，10 人 AI 团队，6 个月建设周期

**背景**：
- 团队 10 人（3 算法 + 5 后端 + 2 前端）
- 需要构建企业级 AI 平台（多租户、高并发、复杂权限）
- 文档量 10 万+ 篇，200GB+，持续增长
- 需要与内部系统深度集成（SSO、数据湖、监控）

**分析**：
- RAGFlow 路线：核心检索可用，但权限、集成、定制化需要大量二次开发
- DIY 路线：完全控制，但需要从零开始

**推荐：DIY（以 LlamaIndex + LangChain 为基础）**
- 团队有能力处理复杂的文档解析和检索需求
- 内部系统集成需要完全的控制权
- 可以参考 RAGFlow 的架构设计理念

**架构建议**：
```
检索层: LlamaIndex (数据加载 + 索引 + 检索)
编排层: LangChain/LangGraph (Agent 编排 + 工作流)
文档解析: RAGFlow DeepDoc 的架构理念自建
         （或用 Unstructured + Marker + Tesseract 组合）
存储层: Milvus (向量) + ES (全文) + Neo4j (图谱)
```

---

### 场景 C：传统企业，无 AI 研发，但 IT 部门运维能力强

**背景**：
- 无 AI 算法工程师
- IT 部门运维能力强（Docker/K8s 熟练）
- 需要内部知识库问答系统
- 文档类型复杂（扫描合同、技术图纸、表格报告）

**分析**：
- 研发门槛：自建 RAG 需要 NLP/AI 背景，团队不具备
- 运维能力：能部署和运维 RAGFlow

**推荐：RAGFlow + 外部咨询**
- 文档解析能力是核心需求（扫描件、表格），这正是 RAGFlow 的长处
- 运维团队可以搞定部署和日常管理
- 业务逻辑集成找外部咨询或使用低代码平台（Dify）

**实施路径**：
1. 由咨询团队完成初始配置（2 周）
2. IT 部门负责文档导入和日常运维
3. 业务部门通过 Web UI 使用
4. 逐步培养内部 AI 能力

---

### 场景 D：有经验团队，但时间紧迫，需要后续深度定制

**背景**：
- 团队 5 人，有 RAG 经验
- 1 个月内需要上线，但 3 个月后需要大量定制功能
- 文档格式中等复杂度

**分析**：
- 短期：RAGFlow 快速上线
- 长期：DIY 满足定制需求

**推荐：混合策略 —— RAGFlow 先行，渐进式替换**

```
第 1 个月：RAGFlow 全量托管
    ├── 文档解析：RAGFlow DeepDoc
    ├── 检索：RAGFlow 内置检索引擎
    └── 业务层：自定义 API 网关

第 2-3 个月：核心组件替换
    ├── 检索层：迁移到 LlamaIndex + 自建向量库
    └── RAGFlow 仅保留文档解析（API 调用）

第 4-6 个月：完全自建
    └── 文档解析也替换为自研方案
```

## 四、成本对比（3 年期 TCO）

| 成本项 | RAGFlow 企业版 | DIY 自建 |
|--------|---------------|----------|
| **人力投入** | | |
| 初始开发 | 0.5 人月（集成） | 6-12 人月 |
| 持续开发 | 0.2 人月/月 | 1-2 人月/月 |
| 运维 | 0.5 人月/月 | 1 人月/月 |
| **基础设施** | | |
| 服务器 | 中等（核心+依赖） | 高（所有组件自建） |
| 数据库 | MySQL+ES 含在部署中 | 需独立配置 |
| GPU | 共享 | 独立 GPU 集群 |
| **许可证** | | |
| 软件费用 | 社区版免费 / 企业版询价 | 全开源，0 元 |
| **风险成本** | | |
| 供应商锁定 | 中等 | 无 |
| 技术债务 | 低（开箱即用） | 自建质量参差不齐 |

**粗略估算**：
- RAGFlow 路线（社区版）：首年约 15-25 万人力成本 + 10 万基础设施
- DIY 路线：首年约 50-80 万人力成本 + 15-25 万基础设施
- **3 年期**：DIY 通常在第 2-3 年追平 ROI（因为后续迭代成本低）

## 五、RAGFlow 的局限性（何时不适合）

### 5.1 技术局限

| 局限 | 影响 | 缓解方案 |
|------|------|----------|
| **检索算法封闭** | 无法自定义检索策略 | 用 API 获取文档后自己检索 |
| **嵌入模型绑定** | 需用 RAGFlow 支持的模型列表 | 使用 RAGFlow API v2 自定义嵌入 |
| **并发限制** | 社区版单实例性能有限 | 企业版支持集群部署 |
| **社区生态小** | 插件和集成较少 | 通过 API 自行集成 |
| **版本更新快** | API 可能变动 | 锁定版本，充分测试后升级 |

### 5.2 业务场景不适配

| 场景 | 原因 | 替代方案 |
|------|------|----------|
| **实时流式处理** | RAGFlow 为批处理设计 | Kafka + Flink + 自建 RAG |
| **超大规模（亿级文档）** | 社区版未针对此规模优化 | Milvus 分布式 + 自建 |
| **需要极端低延迟（<50ms）** | RAGFlow 内部多跳处理 | 简化的向量检索 + 缓存 |
| **深度多模态融合** | 多模态支持有限 | 自建多模态检索管道 |
| **复杂 Agent 工作流** | RAGFlow 以检索为中心 | LangGraph + CrewAI |

## 六、最终决策矩阵

```
文档解析是瓶颈？
  ├── YES → RAGFlow（DeepDoc 是其最强项）
  └── NO  →
        │
        团队有 RAG 研发能力？
        ├── YES →
        │      │
        │      有 Web UI / 管理后台需求？
        │      ├── YES → 先用 RAGFlow，再按需替换组件
        │      └── NO  → DIY（LlamaIndex + LangChain）
        │
        └── NO  →
               │
               需要快速上线？
               ├── YES → RAGFlow 或 Dify
               └── NO  → 招人或外包
```

**核心原则**：让 RAGFlow 做它最擅长的（文档解析与管理），你的团队做最擅长的（业务逻辑与应用集成）。
