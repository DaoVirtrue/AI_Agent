# S2-07：容量规划与扩缩容

## 一、GPU 预热策略

### 问题

LLM 推理的 GPU 资源无法像 Web 服务一样秒级扩容：
- 冷启动：加载模型到 GPU 需要 30 秒 - 5 分钟
- 温启动：从快照恢复需要 10-30 秒
- 热启动：已有模型的扩容需要 1-5 秒

### 策略

```yaml
分层预热策略：

L1 热池（始终运行）:
  - 数量: 预测基准的 120%
  - 用途: 日常流量
  - 扩缩: 不缩到低于此数量

L2 温池（快速启动）:
  - 数量: 已加载模型但未接流量
  - 启动时间: 10-30秒
  - 用途: 小幅度流量增长
  - 触发: CPU > 60%

L3 冷池（按需启动）:
  - 数量: 0 → N
  - 启动时间: 2-5分钟
  - 用途: 大幅度流量增长
  - 触发: 预测模型检测到大促事件

调度策略:
  - 8:00-10:00（早高峰）: L1×1.5 + L2×1
  - 10:00-18:00（平峰）: L1×1.0 + L2×0.5
  - 18:00-22:00（晚高峰）: L1×1.2 + L2×0.5
  - 22:00-8:00（低谷）: L1×0.8
```

## 二、Token 级速率限制

```python
class TokenRateLimiter:
    """
    Token 级别的速率限制。

    为什么需要 Token 级限制？
    - 不同查询消耗的 Token 差异巨大（50 vs 5000）
    - 请求级限制无法防止"单次消耗巨大"的查询
    - GPU 关心的不是请求数，而是 Token 处理量
    """

    def __init__(self, max_tokens_per_minute: int = 1_000_000):
        self.max_tokens = max_tokens_per_minute
        self.window = 60  # 1分钟窗口
        self.token_usage: Dict[str, List[Tuple[float, int]]] = {}

    def allow_request(self, user_id: str,
                      estimated_tokens: int) -> Tuple[bool, str]:
        """检查是否允许此次请求。"""
        now = time.time()
        usage = self.token_usage.get(user_id, [])

        # 清理过期记录
        usage = [(t, tokens) for t, tokens in usage
                 if now - t < self.window]

        # 计算窗口内已使用的 Token
        used = sum(tokens for _, tokens in usage)

        if used + estimated_tokens > self.max_tokens:
            wait_time = self.window - (now - usage[0][0]) if usage else 60
            return False, f"Token 速率限制: 已用 {used}/{self.max_tokens}，" \
                          f"请在 {wait_time:.0f} 秒后重试"

        usage.append((now, estimated_tokens))
        self.token_usage[user_id] = usage
        return True, "OK"

    def get_rate(self, user_id: str) -> float:
        """获取当前使用率。"""
        now = time.time()
        usage = self.token_usage.get(user_id, [])
        usage = [(t, tokens) for t, tokens in usage
                 if now - t < self.window]
        used = sum(tokens for _, tokens in usage)
        return used / self.max_tokens
```

## 三、成本预测性扩容

```python
class CostPredictiveScaler:
    """
    基于成本预测的扩容决策。

    核心思路：
    - 扩容增加成本（更多 GPU 实例）
    - 缩容节省成本
    - 在 SLA 和成本之间找平衡点

    决策公式：
    - 如果 (预期P99延迟 > SLA × 0.8) → 扩容
    - 如果 (预期P99延迟 < SLA × 0.3) → 缩容
    - 如果 (扩容成本 > 预估超时损失) → 不扩容
    """

    def should_scale_up(self, current_qps: float, current_p99: float,
                        sla_p99: float, cost_per_instance: float,
                        penalty_per_timeout: float) -> dict:
        """扩容决策。"""

        # 如果已经接近 SLA 上限，扩容
        if current_p99 > sla_p99 * 0.8:
            return {
                "decision": "scale_up",
                "urgency": "high",
                "reason": f"P99 ({current_p99}ms) 接近 SLA ({sla_p99}ms)",
            }

        # 预测：增加 20% 流量会怎样
        predicted_p99 = current_p99 * 1.3  # 简化模型
        if predicted_p99 > sla_p99:
            return {
                "decision": "scale_up",
                "urgency": "medium",
                "reason": f"预测P99 ({predicted_p99:.0f}ms) 将超过 SLA",
            }

        return {"decision": "no_action"}

    def should_scale_down(self, current_qps: float, current_p99: float,
                          sla_p99: float) -> dict:
        """缩容决策。"""
        # 如果远低于 SLA，可以缩容
        if current_p99 < sla_p99 * 0.3 and current_qps > 0:
            return {
                "decision": "scale_down",
                "reason": f"P99 ({current_p99}ms) 远低于 SLA ({sla_p99}ms)",
            }

        return {"decision": "no_action"}
```

## 四、HPA 配置总览

```yaml
# Kubernetes HPA 完整配置

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: rag-api-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: rag-api

  minReplicas: 3      # 最少3副本（两个正常服务 + 1个冗余）
  maxReplicas: 30     # 最多30副本（成本上限）

  metrics:
    # CPU
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

    # 内存
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80

    # P99 延迟（自定义指标）
    - type: Pods
      pods:
        metric:
          name: rag_response_time_p99_ms
        target:
          type: AverageValue
          averageValue: "2500"

    # Token 处理速率（自定义指标）
    - type: Pods
      pods:
        metric:
          name: token_processing_rate
        target:
          type: AverageValue
          averageValue: "50000"  # 每Pod每秒处理50000 token

  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60
      policies:
        - type: Percent
          value: 100    # 每次最多扩容100%
          periodSeconds: 60
        - type: Pods
          value: 5      # 或每次最多5个Pod
          periodSeconds: 60
      selectPolicy: Max

    scaleDown:
      stabilizationWindowSeconds: 300  # 5分钟稳定窗口
      policies:
        - type: Percent
          value: 10
          periodSeconds: 60
      selectPolicy: Min
```

## 五、大促容量规划模板

```yaml
大促场景规划 (以双11为例):

第1步：预测流量
  - 基准日流量: 10万次/天
  - 大促预期: 100万次/天 (10倍)
  - 峰值 QPS: 1000 (平均QPS的3倍)

第2步：容量计算
  - 单 GPU 处理能力: 20 QPS
  - 所需 GPU: 1000 / 20 = 50 实例
  - 加冗余 20%: 60 实例

第3步：成本预估
  - 单 GPU 日成本: $50
  - 大促日成本: 60 × $50 = $3000/天
  - 提前3天扩容预热 + 延后1天缩容 = 5天
  - 总扩容成本: $15,000

第4步：降级预案
  - 如果实际流量超过预测 2×:
    → 启用请求队列 (排队而非拒绝)
    → 降低模型等级 (GPT-4o → GPT-4o-mini)
    → 关闭非必要功能（文档上传、复杂分析）
    → 缩短上下文窗口 (8K → 4K)
```
