## 根因分析（5 Whys）

```
Why 1: 为什么 RAG API 返回 503？
  → 向量数据库连接超时，检索失败。

Why 2: 为什么向量数据库连接超时？
  → 向量数据库进程 OOM（内存溢出）后崩溃。

Why 3: 为什么向量数据库 OOM？
  → 最近导入了一批超大文档（单篇 50MB+），索引时内存使用
     远超预期，触发 OOM Killer。

Why 4: 为什么超大文档能绕过限制上传？
  → 上传接口没有文档大小校验，也没有在索引前对文档大小
     做预估检查。

Why 5: 为什么没有提前发现这个风险？
  → 缺少文档大小监控和内存使用告警，也没有在上传流程中
     加入资源预估环节。

根因：上传接口缺少文档大小校验和索引内存预估。
```

## 经验教训

```yaml
做得好的地方:
  - 值班工程师响应迅速（1分钟内确认事故）
  - 断路器+缓存回退减少了用户影响
  - 团队协作顺畅，恢复时间在 SLA 内

需要改进的地方:
  - 缺少对大文档的防护机制
  - 向量库监控不够全面
  - 没有文档大小的事前校验
  - 事故通知范围可以更精确（一开始通知了所有人）

关键收获:
  1. 永远不要信任"用户上传的文档"——必须有严格的校验
  2. 每个外部输入都需要资源预估和限制
  3. 降级策略必须提前准备并定期演练
  4. 监控指标要覆盖所有资源维度（CPU/内存/磁盘）
```
