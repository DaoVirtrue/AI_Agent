# S2-06：蓝绿部署流程

> **目的**：零停机部署 + 渐进式流量切换 + 自动回滚

---

## 一、蓝绿部署架构

```
┌──────────────────────────────────────────────────┐
│                 负载均衡器 (Nginx/Traefik)        │
│                   权重: 蓝 100% / 绿 0%           │
│                       │                           │
│           ┌───────────┴───────────┐               │
│           ▼                       ▼               │
│   ┌──────────────┐       ┌──────────────┐        │
│   │  Blue (当前) │       │ Green (新版) │        │
│   │  v2.3.0      │       │  v2.4.0      │        │
│   │  健康 ✅      │       │  健康 ✅      │        │
│   └──────────────┘       └──────────────┘        │
│           │                       │               │
│   ┌───────┴───────┐       ┌───────┴───────┐      │
│   │  Blue DB      │       │  Green DB     │      │
│   │  (共享向量库) │       │  (共享向量库) │      │
│   └───────────────┘       └───────────────┘      │
└──────────────────────────────────────────────────┘
```

## 二、部署流程

### 阶段 0：部署 Green（0% 流量）

```bash
# 1. 部署新版本到 Green 环境
kubectl apply -f deploy/green/

# 2. 等待 Pod 就绪
kubectl wait --for=condition=ready pod -l version=v2.4.0 --timeout=300s

# 3. 健康检查
curl https://green.internal/health
# 预期: {"status": "healthy", "version": "2.4.0"}

# 4. 初始化（预热缓存、加载模型）
curl https://green.internal/warmup
```

### 阶段 1：影子流量测试（Shadow Traffic）

```yaml
# 复制 1% 的真实流量到 Green，但不返回给用户
# 仅用于验证性能和行为

# Istio VirtualService 配置（如使用 Istio）
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: rag-api-route
spec:
  hosts:
    - rag-api
  http:
    - match:
        - headers:
            x-shadow-traffic:
              exact: "true"
      route:
        - destination:
            host: rag-api-green
      mirror:
        host: rag-api-green
      mirrorPercentage:
        value: 100.0
    - route:
        - destination:
            host: rag-api-blue
          weight: 100
```

### 阶段 2：5% 流量切换

```bash
# 将 5% 流量切换到 Green
kubectl patch configmap nginx-config --patch '
data:
  upstream.conf: |
    upstream rag-api {
      server blue:8000 weight=95;
      server green:8000 weight=5;
    }
'

# 重启 Nginx
kubectl rollout restart deployment/nginx

# 观察 10 分钟
# 监控指标: 错误率、延迟、用户反馈
```

### 阶段 3：25% 流量切换

```bash
# 确认 5% 无问题后，提升到 25%
kubectl patch configmap nginx-config --patch '
data:
  upstream.conf: |
    upstream rag-api {
      server blue:8000 weight=75;
      server green:8000 weight=25;
    }
'

# 观察 20 分钟
```

### 阶段 4：100% 流量切换

```bash
# 确认 25% 无问题后，全量切换
kubectl patch configmap nginx-config --patch '
data:
  upstream.conf: |
    upstream rag-api {
      server blue:8000 weight=0;
      server green:8000 weight=100;
    }
'

# 保留 Blue 运行至少 24 小时（便于快速回滚）
```

### 阶段 5：清理旧版本

```bash
# 稳定运行 24 小时后，清理 Blue
kubectl delete -f deploy/blue/
```

## 三、自动回滚触发器

```yaml
自动回滚条件（满足任一即触发）:

1. 错误率:
   - green_5xx_rate > blue_5xx_rate × 2  → 回滚

2. 延迟:
   - green_p99_latency > blue_p99_latency × 1.5  → 回滚

3. 质量:
   - green_hallucination_rate > blue_hallucination_rate × 1.3  → 回滚

4. 黄金数据集:
   - green_golden_pass_rate < blue_golden_pass_rate × 0.95  → 回滚

回滚命令:
  kubectl rollout undo deployment/rag-api-green
  # 或
  kubectl patch configmap nginx-config --patch '
  data:
    upstream.conf: |
      upstream rag-api {
        server blue:8000 weight=100;
        server green:8000 weight=0;
      }
  '
```

## 四、部署检查清单

```
部署前:
  □ 所有测试通过（单元/集成/E2E/负载）
  □ Prompt 回归测试通过
  □ 黄金数据集回归通过
  □ 灰度部署配置已就绪
  □ 回滚方案已准备
  □ 值班人员已通知

部署中:
  □ Green 环境健康检查通过
  □ 5% 流量 → 观察 10 分钟 → 检查指标
  □ 25% 流量 → 观察 20 分钟 → 检查指标
  □ 100% 流量 → 观察 30 分钟 → 确认稳定
  □ 如触发自动回滚 → 执行回滚 → 复盘

部署后:
  □ 持续监控 24 小时
  □ 清理 Blue 环境（24小时后）
  □ 更新部署文档
```

## 五、数据库变更处理

```
RAG 系统的数据库变更（索引结构、元数据表）比较特殊：

原则：蓝绿环境共享数据和向量库，只变更无状态服务。

不可蓝绿部署的变更：
  1. 向量索引结构变更（如修改维度）→ 需离线重建
  2. 元数据表 schema 变更 → 需兼容升级（先扩后收）
  3. 嵌入模型变更 → 需重建全量索引

兼容升级策略：
  1. 新字段 → 先加字段（默认NULL）→ 部署新代码 → 迁移数据
  2. 删字段 → 先部署不再使用的代码 → 再删字段
  3. 改字段 → 先加新字段 → 双写 → 迁移数据 → 删旧字段
```
