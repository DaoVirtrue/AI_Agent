# S2-01：事故分级与响应

---

## 一、事故分级标准

### P0 — 紧急（Critical）

```
定义：核心功能完全不可用，影响所有用户

示例：
- RAG API 返回 5xx 错误率 > 10%
- LLM API 完全不可用（所有供应商同时故障）
- 向量数据库宕机，检索返回空结果
- 安全漏洞导致数据泄露

响应要求：
- 响应时间: 5 分钟内确认
- 恢复时间: 30 分钟内恢复或降级
- 通知范围: 全公司（CTO + VP + 所有相关团队）
- 升级路径: 值班工程师 → 团队负责人 → CTO
```

### P1 — 严重（High）

```
定义：核心功能严重受损，影响大部分用户

示例：
- RAG 回答质量严重下降（幻觉率 > 10%）
- 检索延迟 P99 > 10s
- LLM API 部分供应商故障（一个降级可用）
- 知识库索引损坏，部分文档不可检索

响应要求：
- 响应时间: 15 分钟内确认
- 恢复时间: 2 小时内恢复或降级
- 通知范围: 技术团队 + 受影响业务方
- 升级路径: 值班工程师 → 团队负责人
```

### P2 — 中等（Medium）

```
定义：非核心功能受影响，或核心功能轻微降级

示例：
- 知识库上传功能失败
- 回答质量轻微下降（单一类别问题）
- 缓存命中率显著下降
- 部分用户反馈延迟高

响应要求：
- 响应时间: 1 小时内确认
- 恢复时间: 1 天内修复
- 通知范围: 技术团队
```

### P3 — 低（Low）

```
定义：发现问题但不影响用户使用

示例：
- 非关键页面加载慢
- 日志异常（无关紧要的错误）
- 磁盘使用率超过 80%
- 证书即将过期（>7天）

响应要求：
- 响应时间: 4 小时内确认
- 恢复时间: 1 周内处理
```

### P4 — 建议（Trivial）

```
定义：可优化项，不影响正常使用

示例：
- 文档中的错别字
- UI 显示不美观
- 性能优化建议
- 代码重构建议

响应要求：
- 不需要紧急响应
- 纳入下一个迭代
```

## 二、通知模板

### P0 事故通知

```markdown
【P0 事故告警】RAG 服务核心功能不可用

时间：2026-06-11 14:32
级别：P0 - 紧急
状态：处理中
影响：所有用户无法使用知识库问答功能

当前状态：
- RAG API 返回 503 错误率 45%
- 错误日志：Connection refused to vector database

正在采取的措施：
- 值班工程师已接手（张三）
- 正在检查向量数据库连接
- 已通知数据库运维团队

下一步：
- 预计 15:00 前更新进展
- 如 30 分钟内无法恢复，将切换到只读模式
```

### P1 事故通知

```markdown
【P1 事故告警】RAG 回答质量下降

时间：2026-06-11 16:15
级别：P1 - 严重
状态：调查中
影响：约 30% 用户反馈回答质量不佳

现象：
- 错误率上升到 8%（基线 3%）
- 幻觉率上升到 12%（基线 3%）
- 主要集中在"产品使用"类问题

正在调查：
- 检查最新部署的 Prompt 变更
- 检查嵌入模型是否有更新
- 回滚到上一个已知良好的 Prompt 版本

影响范围：使用产品帮助功能的用户
预计恢复：17:00 前
```

## 三、升级路径

```
值班工程师（一线）
   │ 15分钟无法解决
   ▼
团队 Tech Lead（二线）
   │ 30分钟无法解决
   ▼
工程经理 + 架构师（三线）
   │ 1小时无法解决
   ▼
CTO / VP Engineering（最高级）
```

## 四、事故指挥体系

```
Incident Commander（事故指挥官）：
- 一人负责全局协调
- 记录时间线和决策
- 授权资源调配

Communications Lead（沟通负责人）：
- 更新状态页面
- 发送通知邮件
- 回复客户/内部询问

Operations Lead（运维负责人）：
- 执行技术诊断和修复
- 协调多个团队配合

Scribe（记录员）：
- 记录每一步操作和时间
- 为事后复盘做准备
```
